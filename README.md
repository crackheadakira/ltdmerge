# LTD Merge

ltdmerge is a tool to streamline the process of creating new items in the Mii editor.

- `ltdmerge add` builds a mod from a JSON manifest describing the new parts.
- `ltdmerge merge` combines mods (generated by ltdmerge).

# Installation

Prebuilt binaries for Linux, Windows and macOS are attached to each [release](../../releases). To build from source:

```sh
cargo build --release
```

# Adding parts

```sh
ltdmerge add --base /path/to/romfs --out my-mod manifest.json
```

- `--base` is your romfs dump. It is only read from.
- `--out` is the mod folder to write. The mod is written as `<out>/romfs/...`. A relative path is placed under `./mods/`, so the example above writes `./mods/my-mod/romfs/...`.
- The manifest is a file path, or `-` to read it from stdin. Paths inside the manifest are relative to the working directory.

The whole manifest is checked before anything is written, and every problem is listed at once:

```
the manifest has problems:
  asset 1 texture_name: 'assets/hairback.png' is 150x150, 'Eye000' needs 152x128
  asset 2 template: template part 'Eyebrow99' is not in the base MiiParts table
  asset 3 hair_parts_attach_info: no asset has id 'missing'
```

For every new part, ltdmerge:

- picks the next free index after the vanilla parts;
- adds its row to the parts table (`RSDB/MiiParts`);
- injects its texture or copies and renames its model;
- injects its editor icon;
- appends it to the category's editor order;
- updates the resource size table.

## Manifest

A manifest is a list of assets. Every asset needs a `category`. Everything else is either a source file or a value overriding the template.

```json
{
    "assets": [
        {
            "category": "Eye",
            "texture_name": "assets/eye.png",
            "editor_icon_name": "assets/eye_icon.png"
        },
        {
            "category": "Ear",
            "editor_icon_name": "assets/elf_ear.png",
            "model_unit": { "fmdb": "assets/MiiEar02.bfres" }
        }
    ]
}
```

### Templates

Each new part starts as a copy of a vanilla part, referred to as the template. It inherits the template's layout and settings (default scale and position, movement limits, color options, ...). It also inherits the size and format its texture must have, and its editor icon when you don't supply one.

Every category has a default template (see the table below). Pick another with `template`:

```json
{
    "category": "Mouth",
    "template": "Mouth010",
    "texture_name": "assets/mouth.png"
}
```

Any other field of the part overrides the template's value, for example:

```json
{
    "category": "Eye",
    "texture_name": "assets/eye.png",
    "default_scale": 5,
    "is_selectable_color": false
}
```

The full list of fields per category is in `schema/<Category>.json`.

### Fields

| Field                                                                    | Used by                     |                                                                              |
| ------------------------------------------------------------------------ | --------------------------- | ---------------------------------------------------------------------------- |
| `category`                                                               | all                         | Required. One of the categories below.                                       |
| `template`                                                               | all                         | Vanilla part to start from. Defaults per category.                           |
| `texture_name`                                                           | texture categories          | PNG with the same size as the template's texture.                            |
| `no_lip_texture_name`                                                    | Mouth                       | Optional PNG for the version without lips.                                   |
| `model_unit.fmdb`                                                        | model categories            | `.bfres` (or `.bfres.zs`) with the part's model.                             |
| `model_unit.phcl`                                                        | model categories            | Optional cloth file.                                                         |
| `model_unit_for_hat`, `flipped_model_unit`, `flipped_model_unit_for_hat` | model categories            | Optional variants of the model (see below).                                  |
| `editor_icon_name`                                                       | all                         | Optional PNG for the editor icon. Without it, the template's icon is reused. |
| `editor_mask_icon_name`                                                  | Eye, Mouth, Glass, Faceline | Optional PNG for the color mask icon.                                        |
| `eye_accessory`                                                          | Eye                         | Eyelash, eyelid and highlight settings (see below).                          |
| `id`                                                                     | all                         | A name other assets in the same manifest can refer to.                       |
| `hair_parts_attach_info`                                                 | HairBack, HairAll           | Hair parts this hair can attach (see below).                                 |

### Model variants

Besides its main model, a part's `.bfres` can hold variants, which are picked up by name:

- a hat variant: the name contains `Hat`;
- a flipped variant: the name ends in `_Flip`;
- a flipped hat variant: both.

To choose them explicitly, name the model inside the `.bfres`, optionally with its own cloth file:

```json
{
    "category": "HairBack",
    "model_unit": { "fmdb": "assets/MiiHairBack.bfres" },
    "model_unit_for_hat": {
        "fmdb": "MyHair_Hat",
        "phcl": "assets/hat_cloth.phcl"
    }
}
```

### Eye accessories

Every eye has a row of eyelash, eyelid and highlight settings. It is copied from `eye_accessory.template` (default `Eye000`), and the fields you set override it:

```json
{
    "category": "Eye",
    "texture_name": "assets/eye.png",
    "eye_accessory": {
        "template": "Eye010",
        "eyelash_upper": { "scale": 5 },
        "highlight": { "pos": { "x": 2, "y": -1 } }
    }
}
```

The groups are `eyelash_upper`, `eyelash_lower`, `eyelid_upper`, `eyelid_lower` and `highlight`. Each takes `scale`, `aspect`, `rotate`, `pos` and `default_parts_index`. `eyeline_default_enable` sits beside them.

### Hair parts

A `HairParts` asset takes one `.bfres` holding a model per slot. Slots are found from the model names' suffixes, such as `_Center`, `_MiddleLeft` or `_LowerLeftRight`. To use only some slots, or a different model or cloth per slot, list them in `hair_parts_model_unit`. There, `fmdb` is a model name inside the `.bfres`:

```json
{
    "category": "HairParts",
    "model_unit": { "fmdb": "assets/MiiHairParts.bfres" },
    "hair_parts_model_unit": {
        "middleLeft": {},
        "middleRight": {
            "fmdb": "MyModel_MiddleRight",
            "phcl": "assets/cloth.phcl"
        }
    }
}
```

The slot keys are `center`, `left`, `right` and `both`, plus each of these with the prefix `upper`, `middle` or `lower` (e.g. `upperCenter`, `middleLeft`, `lowerBoth`).

A HairBack or HairAll can attach hair parts, either vanilla ones by name or new ones from the same manifest via `@id`:

```json
{
    "assets": [
        {
            "category": "HairParts",
            "id": "ponytail",
            "model_unit": { "fmdb": "assets/MiiHairParts.bfres" }
        },
        {
            "category": "HairBack",
            "editor_icon_name": "assets/hairback.png",
            "model_unit": { "fmdb": "assets/MiiHairBack.bfres" },
            "hair_parts_attach_info": [
                { "hair_parts_name": "@ponytail", "is_attachable_middle": true }
            ]
        }
    ]
}
```

## Schemas

The [`schema/`](schema) folder holds a JSON schema per category (`schema/<Category>.json`), each describing one asset. Use them for completion and validation in your editor.

They're generated from the code. After changing the manifest fields, regenerate and commit them:

```sh
cargo run --bin gen_schemas
```

# Merging mods

```sh
ltdmerge merge mods/hair-mod mods/eye-mod --base /path/to/romfs --out merged
```

- Takes two or more mod folders, each containing a `romfs/`.
- `--out` works as in `add`. It must not be inside one of the inputs.
- `--base` is optional but recommended. With it, a file a mod left identical to vanilla never overrides another mod's change.

Parts that several mods added at the same index are renumbered. Everything that refers to them follows: the parts table rows, textures, models and icons, the editor orders, eye accessory rows, hair parts attachments and mouth NoLip textures. When two mods change the same vanilla resource or row differently, the last mod listed wins, and a warning names it.

# Limitations

- When merging renames a model, the model names inside the `.bfres` are left as they were, has not been seen to cause any issues yet.
